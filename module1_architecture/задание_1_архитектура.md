## 🎯 Практическое задание по Модулю 1

### Цель

Понять систему «Искорка» целиком до проектирования API: выделить участников, сценарии, границы доменов, сформулировать нефункциональные требования и составить таблицу интеграционных точек.

### Исходные данные

Кинотеатр «Искорка» показывает фильмы для детей и подростков. У него есть онлайн-расписание и система бронирования билетов. Информация о бронях вносится в базу с данными покупателя. Все данные хранятся на одном сервере.

**Четыре задачи для автоматизации:**

1. Узнать наличие мест на сеанс.
2. Забронировать место.
3. Отменить бронь.
4. Изменить время сеанса (администратором).

**Учебное расширение v2** (обязательно учитывать):

- внешняя платёжная система (оплата брони, возврат при отмене);
- система уведомлений (зрителю: «бронь подтверждена», «сеанс перенесён»);
- статусы брони: `PENDING → CONFIRMED → CANCELLED / EXPIRED`;
- удержание места на 10–15 минут до оплаты;
- роли: зритель и администратор.

### Задание 1. Участники и сценарии

**Что сделать:**

1. Выпишите всех **участников** системы: людей и внешние системы. Для каждого укажите, что он делает.
2. Составьте список **сценариев** (use cases) — минимум 6 штук. Для каждого укажите участника и систему, которая его обрабатывает.
3. Заполните **словарь предметной области** — минимум 5 терминов.

**Формат сдачи:** таблица «Участник → Что делает» + таблица «Сценарий → Участник → Система» + словарь.

---

### Задание 2. Домены и границы

**Что сделать:**

1. Выделите **4 домена** системы: Расписание, Бронирование, Платежи, Уведомления.
2. Для каждого домена запишите, что в него **входит**, а что **не входит**.
3. Приведите **2 примера плохого API** (где смешаны домены) и предложите, как их разделить.

**Формат сдачи:** таблица «Домен → Входит → Не входит» + два примера «Плохо → Хорошо».

---

### Задание 3. Нефункциональные требования

**Что сделать:**

1. Сформулируйте **5–7 НФТ** для «Искорки» с **измеримыми** критериями.
2. Каждое требование отнесите к категории: производительность, доступность, согласованность, безопасность, идемпотентность, масштабируемость.
3. Добавьте **2–3 НФТ** специально для сценария «отмена брони» (например, возврат денег не позднее 24 часов, уведомление не позднее 1 минуты).

**Формат сдачи:** таблица «Категория → Требование (измеримое)».

**Плохо:** «Система должна работать быстро».  
**Хорошо:** «Наличие мест отвечает быстрее 300 мс для 95% запросов при 1000 RPS».

### Задание 4. Таблица интеграционных точек

**Что сделать:**

1. Заполните таблицу **всех мест**, где одна система обращается к другой. Минимум **8 строк**.
2. Для каждой точки укажите:
   - **Откуда** и **Куда** (система → система);
   - **Какие данные** передаются;
   - **Нужен ли ответ сразу** (✅ Да / ❌ Нет);
   - **Какая НФТ** важна.
3. Определите, сколько точек **синхронных**, а сколько **асинхронных**.

**Формат сдачи:** таблица «Откуда → Куда → Данные → Ответ сразу → НФТ».

**Подсказка:** строки 1–5 закрываются синхронными API (REST, gRPC, GraphQL), строки 6–8 — асинхронными (очереди, события).

### Задание 5. C4-схема Context

**Что сделать:**

1. Постройте **C4 Context** для «Искорки» в **Mermaid**, **PlantUML** или **Draw.io**.
2. На схеме должны быть:
   - все участники (зритель, администратор);
   - все контейнеры системы (сайт, бронирование, админка);
   - все внешние системы (платёжка, уведомления);
   - все связи с **подписями** (что передаётся).
3. **Чек-лист самопроверки:**
   - [ ] Все участники указаны.
   - [ ] Все внешние системы указаны.
   - [ ] Все связи имеют подписи.
   - [ ] Нет «лишних» связей (например, зритель напрямую к базе).
   - [ ] Границы доменов не смешаны.

**Формат сдачи:** Mermaid-код (вставляется в блокнот) или скриншот схемы + исходник.

### Задание 6. Sequence-диаграмма «Отмена брони»

**Что сделать:**

1. Постройте **sequence-диаграмму** для сценария «отмена брони» в Mermaid.
2. Участники: Зритель → Сайт → Сервис бронирования → Платёжная система → Система уведомлений.
3. Шаги:
   1. Зритель нажимает «Отменить».
   2. Сайт отправляет `DELETE /bookings/{id}`.
   3. Сервис бронирования меняет статус на `CANCELLED`.
   4. Публикуется событие `BookingCancelled`.
   5. Платёжная система возвращает деньги.
   6. Система уведомлений отправляет письмо.

**Формат сдачи:** Mermaid-код sequence-диаграммы.

### Задание 7. Мини-Event Storming

**Что сделать:**

1. Проведите **мини-Event Storming** по четырём сценариям:
   - Наличие мест: `SeatsRequested → SeatsReturned`.
   - Бронь: `BookingRequested → BookingCreated → PaymentProcessed → BookingConfirmed`.
   - Отмена: `CancellationRequested → BookingCancelled → RefundProcessed → NotificationSent`.
   - Смена сеанса: `SessionRescheduleRequested → SessionChanged → NotificationsSent`.
2. Для каждого сценария добавьте **команды** (🟦) и **политики** (🟪).

**Формат сдачи:** стикеры на доске (Miro, Mural) или таблица в Markdown.
